# Deployment

Pixie ships as a single podman-compose service. The `pixie-lab`
CLI writes the compose file + envvars into a directory of the
operator's choosing.

## Directory layout

The recommended layout on the deploy host:

```
/opt/pixie/
    compose.yml
    envvars
    envvars.example
    README.md              <- per-deploy readme, also written by pixie-lab init
    data/                  <- persistent state (state.db, blobs, artifacts, overlays)
```

`compose.yml` is generated by `pixie-lab init` and shouldn't need
hand-edits for a standard deploy. `envvars` carries the site-specific
values. The compose file bind-mounts `./data` as `/var/lib/pixie:Z`;
the `:Z` is an SELinux relabel so the container can write the state dir
on labelled hosts (a no-op elsewhere).

## Lifecycle

The `pixie-lab` CLI drives a deploy directory. Install it with
`uv tool install pixie-lab` (or `pipx install pixie-lab`); each
subcommand takes an optional path, defaulting to the current
directory.

### First deploy

```
pixie-lab deploy /opt/pixie
```

`deploy` writes `compose.yml` + `envvars` (auto-filling a random admin
password and the detected host address), brings the stack up with
`podman compose`, and waits for `/healthz`. It refuses to overwrite an
existing `compose.yml` (so a re-run on a populated directory won't clobber
your stack), but it always (re)writes `envvars` with the resolved values.
Pass `--admin-password` / `--host-addr` to pin those, or edit `envvars`
and re-run `COMPOSE_ENV_FILES=envvars podman compose up -d`.

### Restart vs. teardown

A restart is safe for running targets: pixie respawns every nbdkit +
qemu-nbd export from `state.db` on startup, and the nbdboot initrd
connects with `nbd-client -persist`, so a target whose root is on
pixie's NBD reconnects across a quick bounce.

```
podman restart pixie
```

Taking the container fully down drops those exports. Any target
currently booted `nbdboot` off pixie loses its backing device and
hangs - power such targets off before a teardown, or reboot them after.

### Purge and start from scratch

```
pixie-lab purge /opt/pixie --data
```

`purge` stops and removes the container. It prints what it will do and
asks for a `y/N` confirmation first; pass `-y` / `--yes` for scripted
runs (on a non-TTY it refuses without `--yes` rather than fire
unattended). Flags choose how far the wipe goes:

- `--data` - also delete `data/`: `state.db` (catalog, machines,
  events, exports, overlays, settings), every fetched blob and unpacked
  artifact, and all overlay volumes.
  `data/` is a bind mount (`./data:/var/lib/pixie:Z`), not a named
  volume, so purge unlinks it directly - `podman compose down -v`
  alone would not touch it.
- `--images` - also remove the pixie container image.
- `--all` - also delete the deploy directory (`compose.yml`,
  `envvars`); implies `--data`.

With no flag, purge only stops the container and leaves state in place.
Bring a config-preserved deploy back up with `COMPOSE_ENV_FILES=envvars
podman compose up -d`. For a from-nothing redeploy - regenerated compose +
envvars + a fresh admin password - purge with `--all`, then
`pixie-lab deploy /opt/pixie` on the now-empty directory.

### Upgrade the image

`pixie-lab init` pins the container to a specific published tag, e.g.
`image: ghcr.io/safl/pixie:0.4.0`, in `compose.yml`. To upgrade, point
that tag at the new version and recreate; state in `data/` survives
untouched:

```
# edit compose.yml: image: ghcr.io/safl/pixie:<new-version>
cd /opt/pixie && COMPOSE_ENV_FILES=envvars podman compose pull && \
    COMPOSE_ENV_FILES=envvars podman compose up -d
```

`pixie-lab init --force --image ghcr.io/safl/pixie:<new-version>` will
rewrite `compose.yml` to the new tag for you (it leaves `data/` and
`envvars` alone). If you build the image yourself, tag your build to
match the `image:` line in `compose.yml` (or set `image:` to your local
tag), then `podman compose up -d`; a plain `podman build -t pixie:local`
alone does nothing because compose still references the pinned ghcr tag.

### Back up and restore

All persistent state lives under the `data/` bind mount
(`/var/lib/pixie` in the container): `state.db` (catalog, machines,
events, exports, overlays, settings), `blobs/` (fetched image bytes),
`artifacts/` (unpacked netboot bundles), and `overlays/` (per-alias
qcow2 volumes). There is no state anywhere else, so a backup is a copy
of `data/`, and a restore is putting it back:

```
podman stop pixie
tar czf pixie-backup.tgz -C /opt/pixie data
# ... restore onto the same or a new host:
tar xzf pixie-backup.tgz -C /opt/pixie
COMPOSE_ENV_FILES=envvars podman compose up -d
```

Stop the container first so `state.db` is quiesced (no half-written
WAL). `blobs/` and `artifacts/` are the bulky part; if you can re-fetch
from the catalog, backing up `state.db` alone preserves every machine
binding, and the next Fetch repopulates the bytes.

### Select the live env

The `pixie-flash-*`, `pixie-inventory`, and `pixie-tui` boot modes boot
pixie's live env: the **`pixie-live-env`** disk image (the nosi
`arch-headless` base with the pixie CLI + `pixie-on-tty1` service
injected) booted over ephemeral nbdboot, exactly like the `nbdboot`
mode. Two UI steps set it up:

1. On the **Catalog** page (`/ui/catalog`), Fetch the `pixie-live-env`
   image and its `nosi arch-headless netboot bundle`. Both ship in the
   bundled seed catalog (`PIXIE_SEED_CATALOG`, default on); if your
   catalog is empty, import the release `catalog.toml` first. The image
   is an `img.gz` release asset (its `src` is the latest pixie release's
   `pixie-live-env-x86_64.img.gz`, ~900 MiB compressed to download; it
   decompresses to a ~1.3 GiB image served over NBD); the bundle carries
   the matching kernel + initrd.
2. On the **Live env** page (`/ui/live-env`), paste the fetched image's
   `content_sha256` (shown on its catalog row, or in the release's
   `pixie-live-env-x86_64.content-sha256` asset) into **Image content
   sha** and Save. Equivalently, set `PIXIE_LIVE_ENV_IMAGE_SHA` in
   `envvars`.

Until an image is selected **and** its bundle + blob are fetched, the
`pixie-*` boot modes render the readable `unavailable` plan rather than
booting nothing. For an air-gapped install, mirror the `img.gz` + the
oras bundle and point the two catalog entries' `src` at your mirror.

## Environment variables

The compose file passes the important ones from `envvars`; the rest fall
through to defaults. Two of the names below (`PIXIE_HOST_ADDR`) are read
by the compose file, not the app; the app itself reads `PIXIE_PUBLIC_HOST`
/ `PIXIE_NBD_PUBLIC_HOST`, which the compose file populates from
`PIXIE_HOST_ADDR`. The Settings page (`/ui/settings#deployment`) lists the
app-read vars with their live-resolved values.

### Required

**`PIXIE_ADMIN_PASSWORD`** - password for the `/ui/login` form. Pixie
refuses UI writes when unset. The default `envvars` file ships with
a random placeholder; replace it before exposing pixie beyond
`127.0.0.1`.

**`PIXIE_HOST_ADDR`** - LAN hostname or IP pixie tells iPXE targets to
fetch artifacts from. This is a compose-level convenience var: the
generated `compose.yml` sources it into `PIXIE_PUBLIC_HOST` and
`PIXIE_NBD_PUBLIC_HOST` (the values the app actually reads). Set it to
the pixie host's address on the lab network so target PXE firmware can
reach it; leave the two `PUBLIC_HOST` vars alone unless you split HTTP
and NBD across addresses.

### Common tuning

**`PIXIE_PUBLIC_HOST`** (default: `PIXIE_HOST_ADDR`) - override if
pixie is behind a reverse proxy for HTTP.

**`PIXIE_NBD_PUBLIC_HOST`** (default: `PIXIE_PUBLIC_HOST`) - override
if HTTP is proxied but NBD is direct.

**`PIXIE_LIVE_ENV_EXTRA_CMDLINE`** - kernel-cmdline tokens appended
to every pixie-live-env chain. Common values are hardware-quirk
workarounds; see [](hardware-quirks.md).

**`PIXIE_DEFAULT_BOOT_MODE`** (default: `pixie-inventory`) - boot mode a
freshly-discovered MAC auto-registers with. The default is
non-destructive (collect + post inventory, then exit) and one-shot (the
first inventory POST flips it to `ipxe-exit`, so a PXE-first box does
not re-inventory). Set to `ipxe-exit` for the old exit-by-default
behaviour. See [](boot-modes.md).

**`PIXIE_DATA_DIR`** (default: `/var/lib/pixie`) - state root. Holds
`state.db`, `blobs/` (fetched image bytes), `artifacts/` (extracted
netboot bundles), and `overlays/<alias>.qcow2`
(globally-named single-writer overlay volumes for nbdboot; see
[](boot-modes.md)).

**`PIXIE_LIVE_ENV_IMAGE_SHA`** (default: unset) - the `content_sha256`
of the fetched `pixie-live-env` disk image the `pixie-inventory` /
`pixie-tui` / `pixie-flash-*` boot modes nbdboot. When unset, those
modes render the `unavailable` plan. Overridable live on the Live env
page (see [Select the live env](#select-the-live-env)).

**`PIXIE_SEED_CATALOG`** (default: `1`) - seed a fresh (empty) catalog
from the bundled curated catalog (the nbdboot-tested nosi distros, the
flash-only freebsd images, and pixie's `pixie-live-env`) on first start.
Set to `0` to start with an empty catalog. Runs once and never
overwrites an operator-populated catalog. For the full upstream set, use
**Import full nosi catalog** on the Catalog page (imports the whole nosi
catalog on demand).

### NBD supervisor

**`PIXIE_NBD_BIND`** (default: `0.0.0.0`) - address nbdkit binds
per-image exports to. Under `--network=host` on compose, `0.0.0.0`
reaches the LAN.

**`PIXIE_NBD_PORT_BASE`** (default: `10809`) - first TCP port
reserved for exports; each subsequent export lands on the next free
port.

### TFTP (in.tftpd subprocess)

Pixie serves the PXE first hop with a supervised `in.tftpd` (from
`tftpd-hpa`), started and stopped alongside the app; it is not part of
the FastAPI process.

**`PIXIE_TFTP_ENABLED`** - the application default is off (unit tests
and dev don't bind udp/69, which needs root), but the shipped container
image bakes `PIXIE_TFTP_ENABLED=1`, so the standard compose deploy
already brings TFTP up; you do not need to set it. Set to `0` to disable
it (e.g. if an external TFTP server already serves the iPXE NBPs).
Binding udp/69 needs root; the compose file's `--network=host` running
as root inside the container handles this.

**`PIXIE_TFTP_BIND`** (default: `0.0.0.0`)
**`PIXIE_TFTP_PORT`** (default: `69`) - PXE firmware assumes udp/69.

The Settings page in the pixie UI (`/ui/settings#deployment`)
documents all env vars with their live-resolved values on the running
deploy.

## DHCP handoff

Pixie chains iPXE via TFTP: the DHCP server tells the target's PXE
firmware where to fetch the iPXE bootloader, and iPXE then chains
to pixie's HTTP endpoint. The user-class re-DHCP dance lets one
DHCP config serve both PXE ROM firmware (first pass) and iPXE
firmware (second pass).

```{note}
**Secure Boot must be disabled on PXE targets.** Pixie's iPXE binary,
the nosi kernels/initrds it netboots, and the archiso live env are not
signed by a key in the firmware's trust store, so a Secure-Boot-enabled
target silently refuses to boot the chain. Disable Secure Boot in the
target's firmware (or its BMC). The same applies to booting the usbboot
`.iso` via BMC virtual media. Signing the chain (shim + a signed
bootloader/kernel) is not yet supported.
```

### Legacy BIOS / PXE

```
# dnsmasq
dhcp-boot=tag:!ipxe,undionly.kpxe,${PIXIE_HOST_ADDR},${PIXIE_HOST_ADDR}
dhcp-userclass=set:ipxe,iPXE
dhcp-boot=tag:ipxe,http://${PIXIE_HOST_ADDR}:8080/pxe-bootstrap.ipxe
```

### UEFI

```
# dnsmasq
dhcp-boot=tag:!ipxe,ipxe.efi,${PIXIE_HOST_ADDR},${PIXIE_HOST_ADDR}
dhcp-userclass=set:ipxe,iPXE
dhcp-boot=tag:ipxe,http://${PIXIE_HOST_ADDR}:8080/pxe-bootstrap.ipxe
```

Same shape for both; the difference is the bootfile name in the
first DHCP pass (`undionly.kpxe` for BIOS, `ipxe.efi` for UEFI).
Pixie serves both over its supervised `in.tftpd` from a package-bundled
directory.

## Bootstrap URL

Everything after the iPXE handoff is HTTP against
`http://<PIXIE_HOST_ADDR>:8080/pxe-bootstrap.ipxe`, which chains to
the per-MAC plan at `/pxe/<mac>`. No TFTP dependency past the
initial iPXE fetch.

## Troubleshooting

First stops for anything that misbehaves: the **Events** page
(`/ui/events`) records every action pixie takes with a timestamped kind
you can grep; `podman logs pixie` has the container-side detail; and
`GET /pxe/<mac>` shows the exact plan a given target will receive.

- **A target PXEs but never reaches pixie's HTTP.** The plan points at
  the wrong address. `PIXIE_HOST_ADDR` in `envvars` must be the LAN
  address this box answers on; if it's unset the plans point at
  `127.0.0.1`. Fetch `http://<host>:8080/pxe/<mac>` and check the URLs
  in it.
- **A target loads the iPXE bootfile but the first hop fails.** TFTP
  isn't serving. Confirm the container runs with `--network=host` (so it
  can bind udp/69) and that `PIXIE_TFTP_ENABLED` wasn't set to `0`.
- **`pixie-inventory` / `pixie-tui` / `pixie-flash-*` render
  `unavailable`.** The live env image isn't selected + fetched. See
  [Select the live env](#select-the-live-env).
- **A target silently refuses to boot the chain.** Secure Boot is on;
  the iPXE binary and netbooted kernels are unsigned. Disable Secure
  Boot in the target's firmware (see the note under
  [DHCP handoff](#dhcp-handoff)).
- **A target hangs after a container teardown.** Taking pixie fully down
  drops the NBD exports a booted `nbdboot` target depends on. Power such
  targets off before a teardown, or reboot them after pixie is back.
